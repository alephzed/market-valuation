# PRD v1 - Market Valuation

> Scope note: this is a solo learning/portfolio build targeting a Java/Spring backend role, not a product with external stakeholders. It is kept deliberately thin. Domain terms use the glossary in [`CONTEXT.md`](../../CONTEXT.md); technical decisions are recorded in [`docs/adr/`](../adr/).

## Problem Statement

An investor looking at a market index or equity wants to know whether it is currently over- or under-priced, but the market only shows them the price - not what the price *should* be given fundamentals. There is no easy way to see a defensible, model-based estimate of fair value alongside the live price, to understand *why* that estimate is what it is, or to be told when a tracked Symbol swings into over- or under-valued territory.

The existing implementation answers part of this, but as a Flask/pandas/scikit-learn monolith whose logic is entangled, whose data lives in an in-memory cache with no single source of truth, and whose scheduled work fakes step ordering with staggered start offsets. It cannot be reasoned about, tested, or deployed to a modern serverless target.

## Solution

A system that, for any tracked Symbol, computes a **Valuation**: it derives a model-predicted **Fair Value** from Treasury Yield, Dividend, and Earnings, evaluates it under four **Earnings Scenarios** (Trailing, Forward, Blended, Max Forward), and compares each Fair Value against the live **Market Price** to produce a **Valuation Verdict** (OVERVALUED / UNDERVALUED plus the percentage gap).

Users can maintain a **Watchlist** of Symbols, receive an **Alert** when a Symbol's Verdict crosses a configured threshold, and read a Bedrock-generated **Narrative** that explains a Valuation in plain language (it explains the numbers, it never produces or alters them). Access is tiered (`free` / `premium` / `admin`) via Cognito RBAC.

Delivery is two-phase:

- **Phase 1** - a Spring Boot modular monolith (hexagonal, Spring Modulith) with Postgres as the single source of truth, the Valuation Model reimplemented in Java, and a stateless read API. Runs as a single deployable.
- **Phase 2** - the same domain repackaged behind AWS serverless adapters: Step Functions + Lambda refresh pipeline, DynamoDB derived serving layer, Cognito auth, Bedrock Narrative. (Out of scope for this PRD's issues; see below.)

## User Stories

### Viewing valuations

1. As an investor, I want to see the current Valuation for an index Symbol (e.g. the S&P 500), so that I know whether the market looks over- or under-priced right now.
2. As an investor, I want each Valuation to show a Fair Value under all four Earnings Scenarios, so that I can see how the estimate changes with trailing vs forward earnings assumptions.
3. As an investor, I want each Earnings Scenario to carry its own Valuation Verdict (OVERVALUED/UNDERVALUED and the percentage gap), so that I can judge the degree of mispricing, not just its direction.
4. As an investor, I want to see the live Market Price alongside the Fair Value, so that I understand what the verdict is comparing against.
5. As an investor, I want to see the Model inputs that produced a Fair Value (Treasury Yield, Dividend, Earnings), so that the estimate is transparent rather than a black box.
6. As an investor, I want to request a Valuation for an arbitrary Symbol, so that I am not limited to the S&P 500.
7. As an investor, I want to see the historical series of Market Price versus Fair Value over time, so that I can see whether the market has tended to be over- or under-valued.

### Watchlists

8. As a signed-in user, I want to add a Symbol to my Watchlist, so that the system values it on my behalf.
9. As a signed-in user, I want to remove a Symbol from my Watchlist, so that I stop tracking things I no longer care about.
10. As a signed-in user, I want to view all Symbols on my Watchlist with their latest Valuation Verdict, so that I get an at-a-glance picture of everything I track.
11. As a signed-in user, I want my Watchlist to hold only Symbols (no positions or quantities), so that it stays a tracking tool and not a portfolio manager.

### Alerts

12. As a signed-in user, I want to configure an Alert threshold on a Watchlist Symbol, so that I am notified when its Verdict crosses a level I care about.
13. As a signed-in user, I want to be notified when a Symbol crosses into OVERVALUED or UNDERVALUED, so that I can act without watching constantly.
14. As a signed-in user, I want to be notified when the percentage gap exceeds a set amount, so that I catch large mispricings specifically.

### Narrative

15. As a premium user, I want a plain-language Narrative explaining a Valuation, so that I understand *why* the model reached its verdict without reading the raw numbers.
16. As a user, I want the Narrative to be derived from the computed Valuation and never to change the numbers, so that I can trust the figures are deterministic.

### Accounts and tiers

17. As a visitor, I want to see the public S&P 500 Valuation without signing in, so that I can evaluate the product before committing.
18. As a user, I want to sign in, so that I can access Watchlists and Alerts tied to my account.
19. As a free user, I want access to core Valuations, so that the product is useful without paying.
20. As a premium user, I want access to Watchlists, Alerts, and Narrative, so that I get the higher-value features.
21. As an admin, I want elevated access (e.g. triggering a refresh, managing Calibration), so that I can operate the system.

### Data freshness and calibration (operational, user-visible effects)

22. As an investor, I want Valuations based on recently refreshed Market Data, so that verdicts reflect current conditions.
23. As an investor, I want a future-dated Earnings Scenario to use a projected Treasury Yield from the Treasury Curve Forecast, so that a forward Fair Value is not distorted by today's yield.
24. As an investor, I want a future-dated Earnings Scenario to use a Projected Dividend (compounded by Dividend Growth to the Scenario Date), so that forward estimates account for dividend growth.
25. As the system, I want Coefficients regenerated periodically by Calibration over Shiller Data, so that the Valuation Model stays current.

## Implementation Decisions

Architectural decisions are recorded in ADRs and are binding on this PRD: modular monolith + hexagonal ([ADR-0001](../adr/0001-modular-monolith-hexagonal.md)), Postgres source of truth / DynamoDB derived serving ([ADR-0002](../adr/0002-postgres-source-of-truth-dynamodb-serving.md)), Step Functions orchestration ([ADR-0003](../adr/0003-step-functions-orchestration.md)), Cognito auth/RBAC ([ADR-0004](../adr/0004-cognito-auth-rbac.md)), Java Valuation Model ([ADR-0005](../adr/0005-reimplement-model-in-java.md)), Bedrock Narrative-only ([ADR-0006](../adr/0006-bedrock-narrative-only.md)), Terraform IaC ([ADR-0007](../adr/0007-terraform-for-iac.md)).

### Modules (bounded contexts)

- **Valuation** (core) - Fair Value computation across the four Earnings Scenarios, Valuation Verdict, and the Valuation aggregate. Pure domain, no I/O. Consumes Coefficients and Model inputs; produces a Valuation.
- **Market Data Acquisition** (supporting, anti-corruption layer) - fetches and parses Treasury Yield, Treasury Curve Forecast, Market Data (dividend, yield, growth, PE), Forward earnings estimates, Stock Quote, and Shiller Data from external sources, translating them into clean domain values behind outbound ports.
- **Model Calibration** (supporting) - fits Coefficients by ordinary least squares over Shiller Data and persists them.
- **Identity** (generic) - users, Watchlists, Alert configuration, and RBAC tiers. Kept deliberately thin.

### Read / refresh split

- The **refresh path** is the only thing that touches external sources: it fetches inputs, computes Valuations, and writes results to Postgres.
- The **read path** is stateless and serves persisted Valuations from Postgres; it performs no scraping and no on-the-fly computation. Read freshness equals refresh cadence.

### Domain modeling

- Model the ubiquitous language as value objects rather than bare numeric fields: `FairValue`, `ValuationVerdict`, `EarningsScenario`, `ProjectedDividend`, `Coefficients`, `TreasuryYield`, and so on. Tactical DDD is concentrated on the Valuation core; Identity and Market Data stay light.
- A Valuation is an aggregate owning the four scenario results for one Symbol at one point in time.
- Dividend Yield and PE Ratio are displayed fundamentals, **not** Model inputs; the Model consumes the Dividend amount.

### Persistence

- Greenfield schema driven by the domain model, expressed as Flyway migrations (V1). No `ddl-auto`.
- A one-time migration ports only the historical Earnings/valuation series from the old Postgres schema; Coefficients are re-derived by Calibration, and users are handled by Cognito rather than ported as data.

### API contracts (read path)

- Endpoints for: current Valuation for a Symbol; historical Market Price vs Fair Value series for a Symbol; latest Stock Quote for a Symbol; Watchlist CRUD; Alert configuration CRUD. Responses are proper DTOs mapped from the domain (not hand-assembled JSON).
- Public read access for the index Valuation; authenticated access for Watchlist/Alert/Narrative, gated by RBAC tier.

## Testing Decisions

A good test here exercises **external behavior at a seam, not implementation detail**, and never depends on a live external website. The hexagonal outbound ports of the Market Data Acquisition context (`MarketDataProvider`, `QuoteProvider`, `ShillerDataSource`, and the Treasury sources) are the substitution boundary: live web I/O is hit only by the real adapters, and every other test fakes at the port.

Four seams, highest-first:

1. **HTTP API seam (integration)** - drive the read endpoints through `MockMvc`/`WebTestClient` against a real Spring context backed by a **Testcontainers Postgres**, with outbound ports faked. Verifies request→response behavior end to end.
2. **Application-service seam** - exercise `ComputeValuation` and `Calibration` use cases directly with canned Market Data, Shiller Data, and Quote at the outbound ports. The primary seam for deterministic domain behavior.
3. **Domain seam (unit)** - pure tests of Fair Value math across the four Earnings Scenarios, Valuation Verdict, and Projected Dividend compounding. No I/O.
4. **Adapter seam (isolated)** - Jsoup/POI adapters tested against **saved HTML/xls fixtures**, never live sites, so a source layout change fails one focused parse test rather than the whole suite.

Modules under test: Valuation (seams 2-3), Model Calibration (seams 2, 4), Market Data Acquisition (seam 4), Identity and read path (seam 1). Prior art: none - the current codebase has effectively no tests, so this PRD establishes the pattern.

## Out of Scope

- **All of Phase 2.** Lambda packaging (SnapStart, GraalVM native), Step Functions orchestration, the DynamoDB serving layer, Cognito wiring, the Bedrock Narrative service, and Terraform infrastructure are out of scope for the issues derived from this PRD. Phase 1 assumes a single Spring Boot deployable with Postgres. The domain is designed so Phase 2 is new adapters, not redesign; the Phase 2 backlog is a separate later batch.
- **Watchlist as portfolio.** No positions, quantities, cost basis, or P&L. A Watchlist tracks Symbols only.
- **The Narrative producing or altering numbers.** Bedrock explains a Valuation; it is never in the path that computes one.
- **New valuation methodology.** The Valuation Model stays the existing linear relationship (four Coefficients); this is a faithful reimplementation, not a modeling change.
- **Real-money or brokerage integration.** The system informs; it does not trade.

## Further Notes

- The Phase 1 build is best started as a tracer bullet: the Gradle multi-module + Spring Modulith skeleton with the four context modules and empty ports, returning a stubbed Valuation end to end, then filled in slice by slice.
- Because the domain language is already pinned in `CONTEXT.md`, code should inherit those names directly (`FairValue`, `ValuationVerdict`, `EarningsScenario`, `ProjectedDividend`, `Coefficients`); drift from glossary vocabulary should be treated as a defect.
- Retaining the historical Earnings series is the one irreplaceable data asset (it is computed over time and cannot be re-scraped), which is why it is the only data ported.
